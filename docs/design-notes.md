# 提出物④ ── 制作判断のメモ

## 何を記録するアプリか

「ヨルログ」は、寝る前5分で **3タップ＋ひとこと** だけ残す夜のジャーナリングアプリである。
記録するのは (1) からだ／こころの5段階、(2) 今日「効いた」「削られた」タグ、(3) 問いへの短い答え、の3つ。
自由記述に頼ると疲れた夜には手が止まる。だから入力の主役をタップにし、文章は補助に置いた。
タップだけでも記録は成立し、まとめも生成される。

問いは白紙にしない。その日のコンディションから出し分け（こころが低い夜は出来事を外に置く問い、
調子が良い夜は良さの正体を言語化する問い）、さらに **前夜のAIが置いていった問いを翌晩の一番上に出す**。
「昨日は『思い出せない』と書いていました。今日は、覚えておきたい場面が1つありましたか」——
こう聞かれれば、白紙の前で止まらない。書けない夜のための「ことばが出ない夜」モードも用意し、
単語3つでも記録が閉じるようにした。入力の下限をほぼゼロまで下げることが、継続の設計だと考えた。

## まとめプロンプトの狙い ── LLMに「まとめて」とは一度も頼んでいない

このアプリの設計上の中核は、処理を **抽出 → 決定的集計 → 分析** の3段に割ったことである。

第1段では、各日の記録から点数・タグ・見出しに加えて、
**「本人が自分を評価している言葉」と「本人自身が書いた気づき」を、解釈せず原文のまま抽出**させる。
生成ではなく抽出だと明記し、書かれていなければ空文字を返させる。捏造の余地を仕様から消している。

第2段は **LLMを使わない**。タグごとの効き目（ついた日のこころ平均 − つかなかった日の平均）、
前半と後半の平均差、抽出された言葉の日付つき一覧を、すべてJavaScriptで確定させる。

第3段で、その集計済みの根拠だけを渡して分析させる。出力には〈数値〉と〈本人の言葉の直接引用〉の
両方を必ず入れるよう要求した。**根拠を持たない断定が、そもそも書けない状態にしてから渡している。**

一般論に流れる経路も塞いだ。SYSTEMで本人の語句の引用を毎回強制し、
「お疲れさま」「休息も大切です」のような誰にでも当てはまる文を名指しで禁止。
各フィールドにNG例とOK例を添えた（例文は審査サンプルと無関係な架空の記録を使い、当て込みを避けた）。
取り込んだ日の点数はLLMの推定値であるため、週次プロンプトにその旨を明記し、
「断定の根拠にするときは必ず本人の言葉を添えよ」と指示している。

## 「安心して眠れる締めくくり」をどう設計したか

これは寝る前のつぶやきへの応答であり、一日の締めくくりである。
一方で審査基準は「一般論に終わらないパーソナライズ」を求める。
優しさと精度は、放っておくと逆を向く。そこで SYSTEM プロンプトで
**あたたかさを「具体」として定義**し、両者を同じ方向に向けた。

> 「お疲れさま、無理しないでくださいね」——誰にでも言える言葉は、かえって冷たく響きます。
> 「22時過ぎまで動いて、それでもこうして記録を残しています」——
> その人の今日を見ていた者にしか言えない言葉が、あたたかさになります。
> だから、慰めようとしないでください。その人の今日を、正確に見てください。
> 正確に見られることが、この人にとっての安心になります。

**優しさのために精度を落とすのではなく、精度こそが優しさになる。** これが本アプリの態度である。

構造にも反映した。当初は画面の最後が `tomorrow_question`（明日への問い）だったが、
問いで終わると頭が開いたままになり、眠りに向かわない。
そこで **`closing`（今日を閉じる一言）を独立させ、画面のいちばん最後に置いた**。
「(1)今日の具体に触れる (2)もう終わっていいと伝わる (3)明日に灯りをひとつ置く」の3条件を課し、
根拠のない励ましと願望の押しつけを NG例 で明示的に禁じている。
`tomorrow_question` と `micro_action` はその手前に、破線の静かな枠で
「今夜は、ここは考えなくて大丈夫です」と添えて置いた。
`micro_action` は「もし余裕があれば」の距離感で書かせ、宿題にしない。

## UXで意識した点

配色は夜間向けに、深い紺地へ暖色のアクセント。1画面に主要な操作をひとつだけ置き、
タップ領域は大きく、進捗は3本のバーで示した。生成待ちは呼吸する光ひとつに絞った。
まとめは「見出し → 整理 → 気づき → できていたこと → 明日へ（静かに）→ 締めくくり」の順に並べ、
読み進めるほど身構えが解けて、最後の一文で終わるようにしている。
1項目は最大2文というプロンプト制約も、寝る前に読ませるための設計判断である。

## このアプリならではの工夫

**① 「あなたの物差し」と「実際に効いていたもの」の対比。** ふりかえりの中核に据えた出力。
本人が自分を採点するのに使っている基準を、抽出した本人の言葉から名指しし、
記録上で実際に調子を戻していたものと、赤と緑の二欄で並べて見せる。
田中さんの場合、採点の物差しは「成果が出たか」だが、効いていたのは後輩の相談や同期との時間だった。
**自分を測る物差しと、自分を回復させるものが逆を向いている**——この因果の接続こそが、
複数日の記録からしか出てこない発見であり、単純な要約では原理的に到達できない。
ただし書き方は「間違いの指摘」ではなく「すでに持っているのに数えられていないものを、
そっと手渡す」ことと明示的に指示している。発見の鋭さと、受け取りやすさを両立させるためである。

**② 消えかけている、自分自身の気づき。** 本人が自分で書いた気づきのうち、
その後の記録で触れられなくなっているものを日付つきで指摘する。
「6/5にこう書き、6/8では『この小さいの』に置き換わっている」——
気づきが数日で薄れる現象そのものを可視化する。これも複数日データでしか成立しない。

**③ まとめが次の問いを産む循環。** AIの出力に翌晩の問いを含め、それを翌日の入力ガイドに使う。
まとめが読み物で終わらず、次の記録の入り口になる。

**④ 見出しの背表紙。** その日に付いた見出しが日付とともに積み上がる。
7日分をスクロールすると、それだけで一週間が物語として読める。
「続けたのに変化が見えない」に対して、AIの生成を待たずに視覚で答える部分をつくった。

**⑤ 安全設計。** 深刻な語をローカルで検知して相談窓口を提示し、
プロンプト側でも診断・助言・決めつけを禁じている。判定はAIに委ねず、送信前にブラウザ内で行う。
